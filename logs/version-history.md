# RaceDates — Version History

Version format: `release.major-update.minor-update`
- **release** — increments for a finished, complete build placed in the `Releases/` folder.
- **major-update** — increments when a significant feature or page is completed.
- **minor-update** — increments for small changes, fixes, and tweaks.

Newest entries at the top. When work listed in `current-plan.md` is completed, it is removed from there and recorded here.

## 1.1.4 — 2026-07-30
- **Full adapter health audit, prompted by James asking why Croft and Donington Park showed no events.** Cross-referenced every one of the 64 tracks against events.json. Donington Park actually had events (a display red herring — the real issue was elsewhere); Croft had none; and checking *why* turned into a much bigger find: several adapters had been silently broken for a while, quietly coasting on old cached data via the "keep existing entries" guards (the same protective mechanism added in v1.1.3), which is exactly why nothing looked obviously wrong until someone checked a specific track. Tracks showing zero events dropped from 34 to 25 as a result of this pass.
  - **BTCC adapter was completely dead**: btcc.net was fully redesigned at some point — none of the old selectors (`circuitDatesText`/`ct-span`/`mainHeading`, absolute hrefs) exist in the current markup at all, so it had been matching zero rounds. This is why Croft and Silverstone (both real, confirmed rounds on the actual 2026 calendar) were missing, along with the whole series silently running on stale data. Rewrote the regex against the real current structure (`<a class="calendar-card">` cards) and verified all 10 rounds parse correctly, including both missing ones, against real captured HTML before trusting it.
  - **Oliver's Mount adapter was also dead**: their site started quoting the `data-end-date` attribute and added a `style="display:none"` attribute the old regex didn't account for, so it too had been matching zero events. Fixed and verified against real markup (2 sample events parsed correctly).
  - **A systemic, higher-impact bug found investigating British GT** (which had silently dropped from ~4 events to 1): `Parse-DayMonth`, the shared date parser every single adapter in this file calls, relied on .NET's `ParseExact` with a culture-aware `"MMM"` format — and on this system, `en-GB`'s abbreviated month name for September is **"Sept"** (4 letters), not the standard 3-letter "Sep". Any adapter that built its own 3-letter month abbreviation (British GT's code did exactly this) silently failed to parse every September date; adapters that happened to copy the source site's own "Sept" text (like BTCC's raw scrape) worked by accident. Rewrote `Parse-DayMonth` to match on just the first 3 letters against a fixed month-name table instead of depending on .NET locale data at all — verified against 10 cases (every month format seen this session, plus deliberately invalid inputs) before trusting it. This one fix alone recovered British GT (1→3 events), Straightliners (9→12, no more skipped September dates), and BriSCA F1 (36→42) simultaneously.
  - **Added the same try/catch protection Santa Pod/Castle Combe/Pembrey already had to every adapter that was still missing it** (BSB, British GT, British Hillclimb, Lydden Hill, Straightliners, Lochgelly, BriSCA F1) — previously, a single transient failure on any of these would crash the *entire* script (`$ErrorActionPreference = "Stop"`, no guard), silently skipping every adapter listed after it that day. Confirmed BTCC's fetch failure mid-session (see below) now degrades gracefully instead of taking the rest of the pipeline down with it.
  - **Verified every other adapter's markup against its live site** (BSB, British GT, British Hillclimb, Lydden Hill, Goodwood, Straightliners, BriSCA F1) via captured real HTML rather than assuming — all structurally intact, no further fixes needed there.
  - **A second real duplicate-track bug found along the way**: "Driftland" and "Lochgelly Raceway" are two separate entries in tracks.json pointing to the *identical* Wikidata QID and coordinates — the same physical venue listed twice, which is also why the admin review panel kept flagging "Lochgelly Raceway" as a new discovery (it's Wikidata's entry for a venue we already have, just filed under a different name/id). Not resolved here — deciding which name/id is canonical and merging safely is a call for James, not something to guess at.
  - **Croft and Silverstone are still showing zero events in the committed data** despite the BTCC fix being complete and verified — btcc.net's Vercel bot-protection was blocking every request from this machine by the time the fix was ready, from the cumulative testing load across this whole session. The fix itself is correct (proven against real captured markup, independent of the network), and will show up automatically the next time BTCC's adapter runs successfully — no further action needed, just a delay.
  - **25 tracks still have no adapter at all** (as opposed to a broken one) — mostly small/irregular venues (drag ovals, sprint airfields, a kart circuit, a TV-show test track) that were never in scope for the original adapter set. Listed in `current-plan.md` for future research; building new adapters for these is a separate, larger body of work from today's fixes.
  - Verified in browser: Donington Park's track page now correctly lists all 5 real events across BTCC/BSB/British GT; no console errors anywhere; events.json remains a valid array with no duplicate ids throughout every step of this investigation.

## 1.1.3 — 2026-07-30
- **James confirmed the manual re-run succeeded on GitHub — but checking the actual committed data turned up a third, separate real bug.** The run went green and the bot's "Automated data refresh" commit landed, but comparing before/after event counts per track showed Lochgelly Raceway's 19 events and Oliver's Mount's 6 events had both been wiped to zero — not natural date drift (which explains most of the other small per-track drops), an actual silent data loss.
  - **Root cause**: `Merge-VenueEvents` unconditionally replaced a venue's entire event list with whatever its adapter returned that run — including an empty list. Every adapter's fetch is wrapped in try/catch that returns `@()` on failure (by design, so one bad fetch doesn't crash the whole pipeline) — but that meant a *transient* failure for Lochgelly's or Oliver's Mount's site on this one run permanently deleted their real, previously-good data instead of just leaving it stale for a day. `Merge-SeriesEvents` (used by BTCC/BSB/etc.) already had the correct guard for exactly this case ("adapter returned nothing - keeping existing entries") — `Merge-VenueEvents` was simply missing the same protection, an inconsistency between two near-identical functions.
  - Added the same guard to `Merge-VenueEvents`. Re-ran the pipeline locally to confirm: Lochgelly's adapter succeeded this time (17 fresh events, close to the original 19 — the small difference is normal schedule drift, not a bug), and Oliver's Mount's failed again on this run but this time correctly preserved rather than wiped — though "preserved" still meant preserving the already-zeroed committed state, so its 6 events had to be manually restored from the last known-good commit (v1.1.0) rather than re-fetched, since its site wasn't responding at the time. Not freshly re-verified today, but real data, and it'll self-correct on the next successful automated run regardless.
  - Castle Combe still returned nothing on the real GitHub Actions run too (its bot-protection may be blocking GitHub's runner IPs entirely, not just rate-limiting mine) — no data was lost there since it never had any committed yet, but it remains unconfirmed working. Worth periodic checking rather than assuming it'll self-resolve.
  - Verified in browser: Oliver's Mount's track page correctly lists all 6 events again, no console errors.

## 1.1.2 — 2026-07-30
- **The actual bug behind the nightly failure — v1.1.1 fixed real problems it found along the way, but had the wrong root cause. James re-ran the workflow manually and this time the real error was visible**: `refresh-tracks.ps1:56 — Method invocation failed because [System.DateTime] does not contain a method named 'Substring'`.
  - **Real cause**: `$row.opened.value` (a Wikidata SPARQL date field) is a plain string on Windows PowerShell 5.1's JSON parser, but PowerShell 7 (`pwsh`, what GitHub Actions' ubuntu runners actually use) auto-materialises ISO-looking date strings into real `[datetime]` objects — so `.Substring(0, 4)` (works fine on a string) throws on a DateTime. This had been silently broken this way since the script was first written; it never showed up locally because I'd only ever tested against Windows PowerShell 5.1 (`pwsh` wasn't installed on this machine) and never actually against the PS7 runtime CI uses.
  - **Installed PowerShell 7 locally this time** (`winget install Microsoft.PowerShell`) specifically so this could be verified against the real runtime before pushing again, rather than asking James to burn a third CI run to find out. Added a small `Get-YearFromWikidataDate` helper that handles both a string and a `[datetime]` input, and used it at all three spots in `refresh-tracks.ps1` that extract a year from a Wikidata date field (the SPARQL path that actually failed, plus two more in the entity-claims fallback path that had the identical latent bug but hadn't been hit yet).
  - **Proactively audited `refresh-events.ps1` for the same class of bug**: it's HTML-regex-based everywhere except the Pembrey adapter (v1.1.0), which reads `startDate`/`endDate` straight from a JSON API — exactly the shape that bites. Hardened it to coerce back to a plain `yyyy-MM-dd` string regardless of which shape the parser hands back, so a future PowerShell/runner update can't silently corrupt Pembrey's dates (or the event `id`s built from them) the same way.
  - Verified all of the above by actually running both scripts under real `pwsh` 7.6.4 (not just PS 5.1) — `refresh-tracks.ps1` completed cleanly (64 tracks, correct `opened` years like 1948/1950/1931, proper JSON arrays), and `refresh-events.ps1` completed cleanly with correctly-formatted Pembrey dates. The data these test runs produced was **not committed** — Santa Pod and Castle Combe both hit temporary 403s during this run (repeated local testing today, same rate-limiting pattern noted in v1.1.0) so the fetched snapshot was incomplete; only the script fixes are in this commit, and the next real nightly run (or a manual re-trigger) will produce the actual data update.

## 1.1.1 — 2026-07-30
- **Fixed the nightly automated refresh, which had been silently failing for 5 days straight (2026-07-26 to 2026-07-30).** James spotted it on GitHub's Actions tab and flagged a "Node.js 20 deprecated, GitHub now runs Node.js 24" message as the apparent cause.
  - **That message was a red herring.** It's a routine GitHub-wide deprecation warning about `actions/checkout@v4`'s internal Node version, unrelated to our own scripts (which are pure PowerShell) and not the reason the job failed — confirmed by pulling the run's actual annotations from the GitHub API, which showed the warning as a separate, non-fatal annotation next to the real one: a bare "Process completed with exit code 1" from the "Refresh track data (Wikidata)" step, with no further detail exposed (GitHub now requires sign-in to view raw Action logs, even on public repos).
  - **Root cause diagnosed as Wikidata rate-limiting at the time — turned out to be wrong; see v1.1.2, which has the actual cause.** GitHub only exposes a bare "exit code 1" without sign-in, and everything I could check pointed at an external, unreachable-from-here cause; James manually re-ran the workflow afterwards and the real error was visible on GitHub's own run page. Still wrapped the SPARQL call in try/catch here regardless — that's good defensive practice independent of what actually broke this time.
  - **The real damage was bigger than stale track photos**: because GitHub Actions skips every subsequent step after one fails, the *completely unrelated* race-calendar refresh (`refresh-events.ps1`) was also being skipped every single day — meaning race data had gone stale for 5 days too, not just Wikidata enrichment. Added `if: always()` to both the calendar-refresh step and the commit step in `.github/workflows/refresh-data.yml`, so the two pipelines are now fully decoupled: a failure in one can never again block the other, regardless of cause.
  - **A second, unrelated real bug found while investigating**: `discovered-tracks.json` (the admin page's "new venues to review" feed) was being written as a bare `{...}` object instead of a `[...]` array whenever it held exactly one item — a classic PowerShell 5.1 `ConvertTo-Json` gotcha where piping a single-element array unwraps it. admin.js calls `.filter()` on this data immediately on load, so a bare object there throws and silently breaks the "new venues to review" panel — which is exactly the state the live site had been in (it held exactly one item, "Lochgelly Raceway", for who knows how long). Confirmed empirically: piping a 1-item array through `ConvertTo-Json` produces a bare object, and piping a 0-item array produces an empty string (not even valid JSON) — both wrong.
  - **Fixing that took two attempts** — the first fix (`ConvertTo-Json -InputObject $x`, without a fresh `@()` wrap) traded one bug for a worse one: empirically, passing a `ConvertFrom-Json`-sourced array via bare `-InputObject` (regardless of element count) serializes it as its underlying .NET shape `{"value":[...],"Count":N}` instead of a plain array — which broke tracks.json's *own* write (all 64 tracks, not just the small discovered list) the moment the script re-read its own corrupted output on a second run. Caught this locally before it was ever committed (git had the clean 64-track data throughout; corrupted local files were restored with `git checkout --`). The actual fix, verified against real `ConvertFrom-Json` output at 0/1/many elements before trusting it: `ConvertTo-Json -InputObject @($x)` — a fresh `@()` wrap at the call site sidesteps both quirks at once.
  - Verified in browser: admin page's discovered-venues panel now correctly shows "(2)" and lists both venues (Buckmore Park Kart Circuit, Lochgelly Raceway) instead of rendering blank; tracks page still shows 64/64 tracks; no console errors anywhere.
  - Note for James: the newly-visible "Lochgelly Raceway" discovery (Q114811655) is very likely the *same* real venue we already have listed — our existing record matched a differently-named Wikidata entity ("Driftland", Q48772190) at the same coordinates, so Wikidata's separate "Lochgelly Raceway" entry shows as unclaimed. Worth a look on the review panel to dismiss it as a duplicate rather than auto-adding it as a new track.

## 0.9.1 — 2026-07-21
